# CLAUDE.md

Проект: ветки «Метод 3» (LLM-as-judge с промпт-оптимизацией GEPA/DSPy) и «Метод 6» (SelfCheckGPT + semantic entropy) исследовательского проекта **Assessing the Reliability of Responses in RAG Systems** (SMILES × Alfa Bank). Задача веток — выдавать per-case вероятности faithfulness и relevance для ответов русскоязычного банковского RAG-бота.

## Обязательное чтение перед любой задачей

Весь контекст проекта лежит в `docs/`. Перед реализацией любого компонента прочитай:

1. `docs/00_project_overview.md` — постановка, определения, метрика, гипотезы H1/H4/H5.
2. `docs/01_data_format.md` — канонический формат данных и сплитов.
3. `docs/02_platform_contract.md` — контракт с общей платформой команды (формат predictions, правила порогов и оценки). **Нарушать контракт нельзя.**
4. Спецификацию реализуемого метода: `docs/03_method3_gepa.md` или `docs/04_method6_selfcheck.md`.
5. `docs/05_tasks.md` — декомпозиция работ; веди в нём чекбоксы.

## Жёсткие правила проекта

- **Local models only.** Никаких внешних LLM API (OpenAI/Anthropic/GigaChat). Все LLM-вызовы — только на локальный vLLM-сервер (`llm.api_base` из `configs/config.yaml`). Библиотека `openai` используется исключительно как клиент к vLLM.
- **Сплиты неприкосновенны.** Файлы в `data/processed/` приходят с общей платформы. Не пересоздавать, не перемешивать, не фильтровать. dev-test не использовать ни для каких решений (пороги, отбор промптов, ранняя остановка) — только dev-val.
- **Формат выхода фиксирован.** Каждый метод пишет `predictions/{method}/{variant}/{split}.jsonl`, строки вида `{"id": str, "p_faith": float, "p_rel": float, "meta": {...}}`. Вероятности, не бинарные метки. Бинаризация — только через подбор порогов на val.
- **Вероятности judge-методов** извлекаются из logprobs токенов PASS/FAIL (softmax по паре на позиции вердикта), не из парсинга текста. Fallback-цепочка: logprobs → regex → 0.5/0.5. Кейс не может быть потерян или выброшен.
- **Кэшируй всё дорогое.** Сэмплы Метода 6 и NLI-скоры — поэлементный кэш в `artifacts/`, перезапуск скрипта продолжает, а не пересчитывает.
- **Детерминизм.** Все случайности — через seed из конфига. Каждый прогон сохраняет рядом с predictions файл `run.yaml`: конфиг + git-хэш + seed.
- **Русский язык данных.** Промпты — на русском. NLI/эмбеддинг-модели — только мультиязычные или русские (см. `docs/06_resources.md`).

## Стиль кода

- Python 3.11+, type hints везде, dataclass для структур данных.
- Конфигурация — только `configs/config.yaml`; никаких магических констант в коде (пороги, N сэмплов, имена моделей — всё из конфига).
- Каждый скрипт — идемпотентный CLI-модуль (`python -m src...` с argparse), пригодный к прерыванию/продолжению.
- Тяжёлые импорты (torch, transformers, sentence_transformers) — лениво, внутри функций, чтобы чистая логика была тестируемой без GPU.
- Для чистой логики (агрегация фич, кластеризация, подбор порогов, парсинг вердиктов) — юнит-тесты в `tests/` со стабами вместо моделей. Писать тест вместе с функцией, не после.
- Комментарии и докстринги — на русском, коротко и по делу.

## Политика внешних API (режимы local / cloud)

Правило проекта «local models only» относится к ДАННЫМ, а не к протоколу вызова:

- **Данные проекта (корпус кураторов, любые банковские тройки) — только локальный vLLM.** Ни одна строка из `data/processed/dev_*.jsonl` (кроме `pseudo_*`) не должна уходить на внешний endpoint. Это абсолютное правило.
- **Облачные API разрешены только в cloud-режиме отладки**: публичные датасеты (HaluBench, SberQuAD) и синтетический псевдо-корпус (`pseudo_*.jsonl`, см. docs/07_pseudo_corpus.md). Назначение — обкатка пайплайнов и GEPA-механики до получения GPU/корпуса.
- Режим задаётся профилем конфига: `configs/config.yaml` (local, дефолт) vs `configs/config.cloud.yaml` (облако). Код не должен знать о режиме ничего, кроме `api_base`/`api_key`/`model` из конфига.
- **Защита от утечки обязательна**: перед любым LLM-вызовом проверять, что при cloud-профиле файл данных имеет префикс `pseudo_` или явный флаг `synthetic: true`; иначе — остановка с ошибкой. Реализовать как guard в общем клиенте.
- В облаке использовать ТЕ ЖЕ открытые веса, что локально (`Qwen/Qwen2.5-7B-Instruct`), не «Turbo»/квантованные варианты без необходимости; расхождения чисел cloud vs local в 1–2 пункта — норма (квантизация), финальные числа — только local.
- Перед работой с провайдером выполнить smoke-тест logprobs: запрос с `logprobs=true, top_logprobs=20` и проверка, что top-логпробы реально приходят на токенах вердикта. Без этого облачная отладка Метода 3 бессмысленна (основная ветка кода живёт на logprobs).
- Все числа, полученные в cloud-режиме, помечаются в run.yaml `profile: cloud` и НИКОГДА не попадают в сводную таблицу проекта и отчёт (кроме секции «отладка», если понадобится).

## Чего НЕ делать

- Не оптимизировать промпты/гиперпараметры по dev-test.
- Не менять `src/common/eval_local.py` после его создания без явного запроса — он повторяет замороженный evaluate.py платформы.
- Не добавлять зависимости без необходимости; список — `requirements.txt`.
- Не запускать полные прогоны на всём датасете без предварительного smoke-теста на 5–10 кейсах (флаг `--limit N` обязателен во всех CLI).
- Не коммитить содержимое `artifacts/` и `data/` (в .gitignore).
