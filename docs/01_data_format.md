# 01. Формат данных

## Канонический JSONL (приходит с платформы команды)

`data/processed/{dev_train,dev_val,dev_test}.jsonl`, одна запись на строку:

```json
{
  "id": "case_00317",
  "query": "Какая комиссия за перевод юрлицу?",
  "dialog": ["клиент: ...", "бот: ..."],
  "context": ["текст чанка 1", "текст чанка 2"],
  "answer": "Комиссия составляет ...",
  "faith": 1,
  "rel": 0,
  "markers": ["off_topic_answer"]
}
```

Правила интерпретации:
- `context` — всегда список чанков (даже если один);
- `dialog` может отсутствовать или быть пустым;
- `faith`/`rel`: 1 = PASS, 0 = FAIL; на приватном тесте отсутствуют (None);
- `markers` — подмножество 13 типов; пустой список НЕ значит «ошибок нет»,
  он значит «маркеры не проставлены» (маркеры есть не у всех кейсов);
- `reliable` в файле не хранится, вычисляется: `faith == 1 and rel == 1`.

## Сплиты

- dev_train / dev_val / dev_test ≈ 80/10/10 открытого train, стратификация
  по (faith, rel), group-aware по контексту. Созданы платформой, заморожены.
- Назначение: dev_train — обучение/few-shot-примеры/подвыборка GEPA;
  dev_val — пороги, отбор промптов, калибровка, ранняя остановка;
  dev_test — только финальные замеры ветки перед сдачей в общую таблицу.

## Представление кейса в промптах

Единый шаблон `[Q]/[CTX]/[A]`:
- `[Q]` = история диалога (если есть) + текущий вопрос;
- `[CTX]` = чанки, пронумерованные как `[Чанк i] ...`, разделённые переводом
  строки; при переполнении `llm.max_ctx_chars` контекст усечь с конца с
  пометкой `[контекст усечён]` (ответ и вопрос не усекаются никогда);
- `[A]` = ответ бота как есть.

## Маркеры (13 типов)

Полный словарь с определениями получить у кураторов и положить в
`configs/markers.yaml` в виде `marker_id: "человекочитаемая расшифровка"`.
Известные примеры: `hallucination` (факты вне контекста),
`incomplete_answer` (упущены важные детали), `off_topic_answer` (ответ не на
тот вопрос). Расшифровки используются: (а) в feedback-функции GEPA (H5);
(б) в error analysis.
