## 2. Главный результат этапа (негативный, важный)

**LLM-as-judge без обучения проигрывает поверхностному логрегу на реальном корпусе**
— вся лестница (zero_shot → few_shot → 72B → GEPA-light) ниже surface 0.613/0.598.

Диагноз (не «сломанный судья»):
- извлечение исправно (100% logprobs у 7B);
- **путаницы осей нет**: ячейка (faith=1, rel=0) — p_faith 0.751 у zero_shot
  (на синтетике было 0.24), сама ячейка редкая (27/2245); негативный вывод
  cloud-этапов «off_topic-путаница — главная проблема» на реальном корпусе не
  воспроизводится;
- настоящая проблема — **слабое разделение тонких ошибок**: Δp_faith(faith=1 − faith=0)
  = +0.088 (синтетика: +0.53); судья переуверен в PASS (mean p_faith на
  unfaithful-ячейках 0.65–0.88); recall unreliable всех judge-вариантов 0.24–0.29;
- **размер модели не лечит**: 72B zero_shot 0.589 — в пределах шума от 7B 0.568;
  few_shot 72B хуже (0.524);
- **реальные маркеры-слепые зоны** (matrix `artifacts/alfa_or/marker_signals_val.json`):
  chunk_fact_mixup и missed_chunk_conditions не ловит ни один вариант; few_shot 7B
  лучший на hallucinated_fact (0.667); off_topic ловят только 7B-варианты.

Интерпретация: реальные ошибки бота — упущенные условия, смешение чанков, тонкие
искажения в длинных (p95 4.9k токенов) контекстах; zero/few-shot 7B–72B судья без
дообучения такие ошибки систематически пропускает. Это эмпирика в пользу
supervised-веток (RuModernBERT кураторов: f1-macro 0.62 на их 4782) и аргумент
для H1-дискуссии команды.

## 3. GEPA light-checkpoint (стоп-правило Task 5)

`markers seed 0, train=300 (30% маркерных — `gepa.train_marker_share`, решение
одинаково для markers/plain), auto=light`: 1392 вызова 7B + 6 рефлексий 72B.
**f1_reliable val 0.550 < few_shot 0.572** → по стоп-правилу полные H5-прогоны
{markers, plain} × {0,1,2} НЕ запущены. Эволюция промпта:
`artifacts/alfa_or/m3_gepa_report_markers_seed0.md`.

Оговорка к H5 на этом корпусе: маркеры лишь у 22% unreliable; на val всего
16 маркер-инстансов — H5-сравнение markers-vs-plain будет шумным даже с 3 сидами.

## 4. Метод 6 — статус

- **Сэмплы**: val+test полностью (446 кейсов × 10) — в кэше
  `artifacts/alfa_or/m6_samples/` (главная LLM-стоимость уже оплачена; докупка не
  нужна). Промпт бота — прокси (реальный не выдан; вопрос №7 кураторам).
- **Overlap-резка NLI** реализована и покрыта тестами (окна с перекрытием 128 ток.,
  агрегация max) — длинные реальные чанки больше не теряют сигнал при усечении.
- **Фичи на CPU нереальны**: замер — >8 мин/кейс (446 кейсов ≈ 60+ часов; длинные
  сэмплы × NLI-пары × окна). Помечено **«до GPU»**: на GPU mDeBERTa считает это
  минутами; пайплайн готов (`python scripts/prepare_m6_features.py --config configs/config.alfa_cloud.yaml --split val`).
- train-сэмплы (для p_rel-логрега) не закупались до решения по объёму (полные
  1787×10 или подвыборка 800 — план допускает).

## 5. Решения, ожидающие пользователя

1. **GEPA-эскалация**: (а) стоп до vLLM/ответов кураторов (рекомендую — light
   ниже few_shot, medium на OpenRouter вероятнее всего деньги в шум);
   (б) дешёвое честное H5-сравнение light 2×3 несмотря на слабый абсолют;
   (в) medium-бюджет.
2. **m6**: ждать GPU для фич (рекомендую) или считать val-фичи на CPU ~сутки.
3. **Вопросы кураторам** (docs/12 §5) — ответы разблокируют full_query, промпт
   бота, трактовку 18 аномальных маркеров.

## 6. Стоимость этапа (OpenRouter)

~6.5k вызовов 7B (zero/few × сплиты, GEPA-light 1392, m6-сэмплы 4460) +
~450 вызовов 72B (абляция) + 6 рефлексий 72B. Порядок единиц долларов.
Кэши поэлементные — перезапуски бесплатны; смена профиля на vLLM не
инвалидирует predictions (но кэш судьи привязан к model-строке).
