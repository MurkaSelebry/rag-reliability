# 12. Этап 0a — онбординг реального корпуса кураторов

**Дата:** 2026-07-08. **Данные:** `data/data/data.zip` → `data/raw/alfa/data.csv`
(2245 строк — часть будущих ~5k). **Периметр:** данные объявлены владельцем
открытыми; внешние вызовы разрешены явным opt-in'ом `guard.allow_real_data`
(см. `configs/config.alfa_cloud.yaml`); дефолт guard'а блокирует.
Все числа этого дока — из `artifacts/alfa_eda.json` (`python -m tools.eda_alfa`).

## 1. Схема и адаптация

CSV кураторов: `full_dialog` (реплики «Ассистент:/Клиент:/Оператор:»), `answer`,
`chunk_1..8`, `binary_relevancy`/`binary_faithfulness`, `markers` (repr-строка списка).
Адаптер `src/data/alfa_loader.py` → канонический `Case`:
- `id = alfa_ + sha1(dialog+answer)[:12]` — детерминирован от содержимого
  (переживёт доливку до 5k и перестановку строк);
- `query` = последняя реплика «Клиент:» (у кураторов есть колонка `full_query`,
  нам не выдана — вопрос №2 ниже);
- `dialog` = весь диалог построчно; `context` = непустые чанки; метки → int;
  `markers` через `literal_eval` (ошибка → `[]` + meta-флаг);
- `meta = {synthetic: false, source: alfa, no_client_turn}` — префикс `alfa_` и
  `synthetic: false` держат guard.

Live-проверка: **2245 кейсов, 623 unreliable, 158 с маркерами, 15 без реплики
клиента** — совпало с ручным разбором CSV.

куда менее частотна, чем в синтетике (25%).

### Маркеры (158 кейсов; 140/623 unreliable = 22%)

Топ-5: hallucinated_fact 35, answer_for_operator 27, chunk_fact_mixup 27,
irrelevant_chunk_used 25, off_topic_answer 19. Оси (`marker_axis` в json):
большинство маркеров бьют по **faith** (faith0_share 0.86–1.00); по обеим осям —
off_topic_answer (0.89/0.89), answer_for_operator (0.85/0.78),

**Аномалия: 18 кейсов с маркерами при reliable=1** (ids в
`alfa_eda.json: anomaly_markers_reliable1`); преобладают incomplete_answer (6),
reveals_ai_identity (5), answer_for_operator (4) — похоже на «минорные ошибки,
не меняющие метку», но требует подтверждения (вопрос №1).

## 3. Provisional-сплиты (`src/data/make_splits.py`)

- **group** (дефолт): дедуп 12 точных дублей → группировка по нормализованному
  последнему запросу → жадная детерминированная раскладка 80/10/10:
  **train 1787 / val 223 / test 223** (reliable 72.5/75.3/68.2%). Группа целиком
  в одном сплите — утечки между сплитами через near-дубли нет.
- **curator**: точное воспроизведение схемы ноутбука кураторов
  (train_test_split 80/20, stratify=reliable, seed 42, без val):
  **1796/449** — только для сравнимости с их бейзлайном.

**Сплиты provisional** — замещаются каноническими сплитами платформы при их
появлении (скрипты идемпотентны, id от содержимого — кэши переживут).

## 6. Следствия для плана

- Маркеры у 22% unreliable → GEPA-feedback разрежен; в подвыборку train маркерные
  кейсы поднимаются до 30% (`gepa.train_marker_share`, одинаково для markers/plain).
- Ячейка (1,0) редкая → «путаница осей» перестаёт быть главной проблемой судьи
  (подтверждено этапом 1); главная проблема — слабое разделение тонких ошибок.
- Alignment-collapse m6 на реальном боте ожидаем выше синтетики — см. docs/13.
