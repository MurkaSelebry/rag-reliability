# 02. Контракт с платформой команды

Общая платформа проекта (другая ветка) владеет: каноническими сплитами,
замороженным `evaluate.py`, сводной таблицей результатов. Наши ветки обязаны
соответствовать её контракту.

## Формат predictions (выход любого метода)

`predictions/{method}/{variant}/{split}.jsonl`:

```json
{"id": "case_00317", "p_faith": 0.83, "p_rel": 0.12, "meta": {"mode": "gepa", "raw": "..."}}
```

- `p_faith`, `p_rel` ∈ [0,1] — вероятность PASS по оси. Всегда вероятности,
  никогда не жёсткие 0/1 (кроме honest-fallback 0.5/0.5 при полном отказе парсинга).
- Каждый `id` входного сплита обязан присутствовать ровно один раз.
- `meta` — свободное поле: сырой вывод судьи (усечённый), n_clusters и т.п.
  Нужен для error analysis.
- Рядом с predictions — `run.yaml`: полный конфиг прогона, git-хэш, seed,
  дата, стоимость (медиана мс/кейс, число LLM-вызовов на кейс).

## Правила оценки (повторены в src/common/eval_local.py)

1. Пороги `t_faith`, `t_rel` подбираются сеткой (шаг 0.01) ТОЛЬКО на dev_val,
   максимизируя f1-macro(reliable), где предсказание
   `reliable_hat = (p_faith >= t_faith) AND (p_rel >= t_rel)`.
2. Найденные пороги применяются к dev_test без изменений.
3. Репортим: f1_macro_reliable (primary), f1_macro_faith, f1_macro_rel,
   долю fallback-кейсов, стоимость.
4. Для прогонов с обучением/оптимизацией — минимум 2–3 seed, mean±std.
5. Финальные числа в общую таблицу считает платформенный evaluate.py по нашим
   predictions-файлам; eval_local — только для разработки, его числа должны
   совпадать с платформенными (это проверяется на первом сданном файле).

## Стоимость (обязательная колонка таблицы)

Каждый метод замеряет на dev_test: медиану времени на кейс (мс), число
LLM-вызовов на кейс, пиковую VRAM. Метод 6 дополнительно — кривую
качество/цена по N сэмплов (3/5/10).
