# 07. Cloud-режим и псевдо-корпус для отладки

## 7.1 Политика API (краткая версия — полная в CLAUDE.md)

| Что | Local (vLLM) | Cloud (внешний API) |
|---|---|---|
| Корпус кураторов (`dev_*.jsonl`) | да | **НИКОГДА** |
| Псевдо-корпус (`pseudo_*.jsonl`) | да | да |
| Публичные датасеты (HaluBench, SberQuAD) | да | да |
| Финальные числа в таблицу/отчёт | да | нет |
| Обкатка кода, промптов, GEPA | да | да |

Профили: `configs/config.yaml` (local) и `configs/config.cloud.yaml` (облако;
отличаются только `llm.api_base`, `llm.api_key`, `llm.model`,
`llm.reflection_*`). Обязательный guard в общем LLM-клиенте: при cloud-профиле
допускаются только кейсы с `synthetic: true` / id с префиксом `pseudo_`,
иначе — исключение до отправки запроса.

Smoke-тест провайдера перед работой (первая задача cloud-режима):
один запрос с `logprobs=true, top_logprobs=20`; убедиться, что в ответе
присутствуют top-логпробы по токенам, и что токены PASS/FAIL восстановимы
(целиком или склейкой BPE-подтокенов). Провайдер без top_logprobs для
Метода 3 непригоден — основная ветка извлечения вероятностей не отладится.

## 7.2 Псевдо-корпус: спецификация генерации

Назначение: ~200–400 русскоязычных кейсов с известными синтетическими метками
для отладки всех пайплайнов до получения корпуса кураторов. Метки синтетические,
поэтому числа на псевдо-корпусе не доказывают гипотезы и не идут в отчёт.

Источник пар (вопрос, абзац): SberQuAD (HF: `kuznetsoffandrey/sberquad`,
split train, случайная подвыборка, не более одного кейса на абзац) или свой
jsonl `{"question", "paragraph"}`. Альтернатива — RuBQ.

Типы кейсов и метки (генерация ответов — LLM по промпту типа):

| Тип (kind) | Как генерируется ответ | faith | rel | markers |
|---|---|---|---|---|
| clean ×2 | точный ответ строго по абзацу | 1 | 1 | [] |
| hallucination | ответ по абзацу с намеренной подменой одного факта/числа/даты на правдоподобный неверный | 0 | 1 | [hallucination] |
| incomplete_answer | верный, но намеренно неполный ответ: опущена важная деталь/оговорка из абзаца | 0 | 1 | [incomplete_answer] |
| off_topic_answer | верный по абзацу ответ про ДРУГОЙ аспект абзаца, не про заданный вопрос | 1 | 0 | [off_topic_answer] |

Пропорция в миксе: 2/1/1/1 (clean/halluc/incomplete/off-topic) — грубая
имитация дисбаланса в сторону положительных меток.

Контекст кейса: абзац-источник + 1–2 случайных дистракторных абзаца из того же
пула, порядок чанков перемешивается (имитация retrieved-контекста RAG).

Выход: канонический формат платформы (docs/01) + `"meta": {"kind": ...,
"synthetic": true}`; сплиты `pseudo_dev_{train,val,test}.jsonl` 80/10/10,
фиксированный seed. Генерации кэшируются поэлементно; CLI с `--n`, `--limit`,
`--source`, `--seed`.

Контроль качества: вручную просмотреть по 5 кейсов каждого типа — искажение
действительно есть, off-topic действительно верен по абзацу. Плохие промпты
генерации чинить до масштабирования.

Побочная ценность: это репетиция синтетической аугментации по таксономии
маркеров, которая может пригодиться команде на основном корпусе (Lynx-style
perturbations).

## 7.3 Специфика OpenRouter (выбранный провайдер)

Профиль: `configs/config.cloud.yaml`. Отличия от локального vLLM, которые
должен учитывать код (все — через конфиг, без if-ов по провайдеру):

1. **ID моделей другие**: `qwen/qwen-2.5-7b-instruct` вместо
   `Qwen/Qwen2.5-7B-Instruct`. Имя модели всегда берётся из конфига — нигде
   не хардкодить.
2. **Роутинг между провайдерами**: под одним ID OpenRouter прячет несколько
   нижележащих провайдеров с разным поведением (квантизация, поддержка
   параметров). Обязательно передавать `llm.openrouter_extra_body` из конфига
   в `extra_body` каждого запроса: `require_parameters: true` (роутить только
   туда, где поддержаны logprobs/top_logprobs) и `allow_fallbacks: false`
   (без тихой подмены провайдера). После первого успешного smoke-теста
   зафиксировать конкретного провайдера через `provider.order`.
3. **Ключ** — из переменной окружения `OPENROUTER_API_KEY`; подстановку
   `${VAR}` в значениях конфига должен уметь загрузчик конфига.
4. **Smoke-тест logprobs (задача №1)**: chat completions с
   `logprobs=true, top_logprobs=20` и коротким принудительным ответом
   формата `FAITHFULNESS: PASS`. Проверить: (а) top-логпробы приходят;
   (б) токены PASS/FAIL восстановимы (возможна разбивка на BPE-подтокены —
   тогда матчить склейкой); (в) при повторных запросах отвечает один и тот же
   провайдер (поле `provider` в ответе OpenRouter). Провалено — сменить
   `provider.order`; не нашлось рабочего — сменить провайдера на
   DeepInfra/Nebius напрямую (меняется только этот yaml).
5. **Параметр n (Метод 6)**: не все нижележащие провайдеры поддерживают
   `n>1` в одном запросе. Клиент обязан иметь fallback: если ответ содержит
   меньше сэмплов, чем запрошено, — добрать отдельными запросами. Дизайн
   кэша от этого не меняется.
6. **Reflection-LM**: 32B на OpenRouter может отсутствовать — в конфиге
   стоит `qwen/qwen-2.5-72b-instruct`; для отладки GEPA-механики это даже
   лучше, но помнить: боевые прогоны рефлексии — локальная 32B.
7. **Выходы отдельно**: cloud-прогоны пишут в `predictions/cloud/` и
   `artifacts/cloud/` — физически не смешиваются с боевыми результатами.

2. Сгенерировать псевдо-корпус (`--limit 10` сначала, глазами проверить).
